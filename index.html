01

Context

Why this page reads the way it does.

Most testers I know move between projects every few months. I have spent the last year on one fintech application and four ways of reaching it — Android, iOS, web, and USSD over the mobile network. Same product, four different sets of failure modes, which is the part that keeps the job interesting.

A build lands and the first question is always the same: what broke? Getting an honest answer quickly is most of the job. That is why the automation matters to me less as a technical exercise and more as a way of buying time — fifty-plus smoke and SIT cases running unattended means the failures that reach a person are the ones a person is actually needed for.

Before that I spent eight months as a testing intern on in-house web applications at Senseops Tech Solutions, writing cases straight from requirement documents and reporting what broke. Not glamorous, and it is where I learned to read a requirement properly instead of testing the screen in front of me.

How a defect gets closed

  1. i

    Reproduce it exactly

    Same device, same build, same screen — otherwise the ticket comes back.

  2. ii

    Log it usefully

    Steps to reproduce, screenshots, console logs, request payloads. A developer should not have to guess.

  3. iii

    Retest the original path

    The reported flow first, then the neighbours it might have disturbed.

  4. iv

    Close on evidence

    Not on the status change. On a regression pass that stays clean.

Projects

Three pieces of work — one built and tested, two tested. Each is laid out differently because they are different problems.

5.1

Library Management System

Java · JDBC · SQL

A small CRUD system with user login. The interesting part was never the create and read — it was proving that a delete in one module didn't leave a row stranded in another.

I wrote unit and integration test cases across the modules, checking that data stayed consistent when one part of the system acted on a record another part was still holding.

How I approached this

The risk was never the CRUD itself — it was a delete in one module leaving a record another module still held. Unit tests pass happily in that situation. It is only the integration pass that notices the data quietly drifting apart.

5.2

AI-Powered Plant Health Detection

Python · CNN · Flask

My part was the interface, not the model. A deep-learning plant disease classifier behind a Flask UI — and the job was making sure the front end behaved when the prediction underneath it was wrong, slow, or missing.

Functional coverage on the Flask interface, the backend prediction path, and a set of edge-case UI inputs where the image the user picks is not what the form expects.

How I approached this

A classifier returning the wrong leaf is a model problem, not a defect I can log. What is mine to test is the Flask layer around it — whether the interface stays honest when the prediction underneath is wrong, slow, or simply missing.

5.3

Weather Forecasting Web App

HTML · CSS · JavaScript · OpenWeather API

Two halves of one feature: a third-party API that can return anything, and a front end that has to behave sensibly whatever comes back.

I checked the OpenWeather responses for accuracy before trusting them, then ran cross-browser functional tests on the front end to make sure the page held up wherever it was opened.

How I approached this

Any third-party API fails in ways the specification never mentions. So the useful question was never does the request work, but what does the page do when it doesn't — empty payloads, error codes, and a network that gives up halfway through.

Break My UI

A deliberately imperfect component. One defect is seeded on purpose — find it before you trust the label.

incident-filterv0.3

demo · not real data

A demo incident list. Its status filter contains one deliberate defect.
IDSummaryStatusSeverity

Count the rows yourself. A good tester does.

PORT-0001 Filter count disagrees with rendered rows

Severity
Low — nothing crashes
Found by

Intentional
yes, seeded for this page

What happens. Filtering by Closed renders three incidents, but the number beside the filter says two.

Why. INC-106 is stored as "Closed ", with a trailing space. The count compares the raw string; the table renders a trimmed one. Two different answers from the same row — and the label is the one nobody checks.

The fix. Trim before comparing, and derive the count from the same collection the table renders, so the two can never disagree again.

That is the defect class I look for first. Not a crash — two parts of the interface telling different stories about the same data.
