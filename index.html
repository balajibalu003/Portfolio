About

What I do, and what I'm actually good at.

I've spent the last year testing one fintech application across Android, iOS, the web, and USSD over the mobile network. Same product, four ways of reaching it, and four different sets of failure modes.

Most of my work is functional, regression, smoke, sanity and exploratory testing, plus integration and acceptance testing as features move from first build to release. I validate REST APIs in Postman — payloads, status codes and edge cases — before anyone opens the UI.

I've automated 50+ smoke and SIT cases so a new build proves itself before a person looks at it. Defects go into Jira with reproduction steps, screenshots and logs, and I retest fixes with the developers until they hold.

I also use AI tools to help write test cases, draft test plans and debug automation scripts, which has cut a surprising amount of test preparation time.

How a defect gets closed

  1. Reproduce it exactlySame device, build and screen — otherwise the ticket comes back.
  2. Log it usefullySteps, screenshots, console logs, request payloads.
  3. Retest the original pathThe reported flow first, then its neighbours.
  4. Close on evidenceNot the status change — a clean regression pass.

What happens. Filtering by Closed renders three incidents, but the number beside the filter says two.

Why. INC-106 is stored as "Closed " with a trailing space. The count compares the raw string; the table renders a trimmed one. Two different answers from the same row — and the label is the one nobody checks.

The fix. Trim before comparing, and derive the count from the same collection the table renders, so the two can never disagree again.

That is the defect class I look for first. Not a crash — two parts of the interface telling different stories about the same data.
